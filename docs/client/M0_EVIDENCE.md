### 服务恢复后的补测

测试 IP 入口恢复，HTTPS 登录、新租约和清理正常。普通用户及管理员身份下，预先向显式 DNS 解析固定测试目标、通过 SOCKS 请求其公网 IPv4 并保留 `example.com` 的 Host/SNI 后，真实 HTTPS、activate、立即 renew、再次转发和回收通过。系统 DNS 查询固定测试域名失败，显式备用 DNS 查询成功；直接经网关请求域名的 HTTPS 返回 `SOCKS_TARGET_EOF_PHASE_TLS_HANDSHAKE`。不能将固定 IP 成功作为系统或网关 DNS 验收。

TUN 使用相同 IPv4 对照仍失败。改为先执行真实 TUN 探测，再执行 SOCKS 辅助诊断；关闭严格路由和改用 OS 网关选路的独立诊断均未解决问题，默认仍启用严格路由。错误包括 `TUN_TARGET_TIMEOUT` / `TUN_HTTPS_FORWARDING_FAILED`、`SOCKS_TARGET_TIMEOUT_PHASE_TLS_HANDSHAKE`。核心记录选择 LF-TUNNEL 不能代替目标转发成功，原型不因此 activate。

抓包改为所有组件、显式原始包标志后仍为空。最后一轮在启用 TUN 前进行了固定目标 TCP 握手校准，握手成功但 pcapng 仍只有 144 字节；ETL 转文本只有 3 条头部事件。这说明抓包工具链的可观测性尚未建立，不能据此断言没有流量。校准是明确的启用 TUN 前直连，不能作为 VPN 证据。最近对照 `LightflowM0-03a1198f778e` 正常回收后快照一致，检查耗时 2248 ms、含证据处理的总清理 4507 ms；仍未验收强杀恢复。

用户指定测试控制面改为 `https://lightflow.u26d.local:8443`，Windows 已解析到 S0 地址，但当前测试证书返回 `CONTROL_CERT_NAME_MISMATCH`。原型默认使用新域名，保留严格 CA/主机名校验；只允许通过显式 `-control` 选择旧测试 IP 作对照，没有自动降级或跳过校验。等待服务端增加对应 DNS SAN 并重载 HTTPS 入口。网关仍为原测试地址/端口，未擅自替换公网测试目标。

## 已发现并纠正的问题

1. Windows 上账号文件实际名称含 `~`；未输出文件内容。包装脚本可见提示这一测试文件别名，直接 Go 探测通过显式 `-account` 使用该文件。
2. 直接完整配置加载时自定义 CA 未进入代理初始化使用的信任池，实测 `CORE_CA_UNTRUSTED`。经拒绝转发 bootstrap → 受保护管道 reload 顺序后，全局/智能真实转发均通过；详见基线中的源码推断与实测边界。
3. 初始管道字符串比较用 `GA`，Windows 实际映射为 `FA`，导致工具误判 ACL。现显式使用 `FA` 并比较实际受保护 DACL；不放宽允许身份。不同用户实际连接拒绝测试仍待执行。
